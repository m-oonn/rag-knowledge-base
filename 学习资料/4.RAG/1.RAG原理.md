# Day 10：RAG 原理

> RAG（Retrieval-Augmented Generation）是你项目一的核心技术，也是面试必考题。
> 今天彻底搞懂：什么是 RAG、为什么需要它、每个环节怎么工作。

---

## 一、为什么需要 RAG？

### 1.1 大模型的两个致命问题

**问题 1：知识过时**
- 模型训练数据有截止日期（如 2024 年 4 月）
- 问它"2025 年的新政策"，它不知道
- 公司内部文档、最新产品手册，它更不可能知道

**问题 2：编造内容（幻觉）**
- 问它不知道的东西，它不会说"不知道"
- 它会一本正经地编造看起来正确但实际错误的回答
- 在企业应用中这是不可接受的

### 1.2 RAG 怎么解决？

**核心思路**：先检索相关文档，再把文档喂给模型，让模型根据文档回答。

```
传统 LLM:
  用户问题 → 模型（凭记忆回答）→ 可能过时/编造

RAG:
  用户问题 → 检索知识库 → 找到相关文档 → 文档+问题一起给模型 → 基于文档回答
```

**类比**：开卷考试 vs 闭卷考试
- 闭卷（普通 LLM）：凭记忆，可能记错
- 开卷（RAG）：翻书找答案，更准确

## 二、RAG 完整流程

### 2.1 两个阶段

```
=== 阶段一：索引（离线，只需做一次）===

文档 → 分割成小段 → 每段转成向量 → 存入向量数据库
 PDF    chunk1          [0.1,0.3,...]    Chroma
 Word   chunk2          [0.2,0.1,...]
 MD     chunk3          [0.4,0.2,...]


=== 阶段二：查询（在线，每次用户提问都执行）===

用户问题 → 转成向量 → 在向量库中找最相似的几段 → 拼成Prompt → LLM生成回答
"什么是xx" → [0.1,0.3,..] → chunk1,chunk3       → "根据文档..." → "xx是..."
```

### 2.2 流程图

```
                    ┌─────────────────────────────────────┐
                    │         离线索引阶段                  │
                    │                                     │
  PDF/Word/MD ──→ 文本解析 ──→ 文本分割 ──→ Embedding ──→ 向量数据库
                    │                                     │
                    └─────────────────────────────────────┘

                    ┌─────────────────────────────────────┐
                    │         在线查询阶段                  │
                    │                                     │
  用户问题 ──→ Embedding ──→ 向量检索 ──→ Top-K文档 ──→ Prompt ──→ LLM ──→ 回答
                    │                                     │
                    └─────────────────────────────────────┘
```

## 三、核心概念详解

### 3.1 Embedding（向量化）

**问题**：计算机不理解文字，怎么判断"苹果手机"和"iPhone"是相似的？

**解决**：把文字转成一串数字（向量），语义相近的文字在向量空间中距离也近。

```
"苹果手机" → [0.12, 0.85, 0.33, ...]   ← 512维或768维的向量
"iPhone"   → [0.13, 0.84, 0.35, ...]   ← 和苹果手机很接近！
"今天天气" → [0.91, 0.02, 0.67, ...]   ← 和上面两个差很远
```

**谁来做 Embedding？**
- 云端：OpenAI text-embedding-ada-002
- 本地：sentence-transformers（免费，Day 12 详细学）
- Ollama 也可以跑 Embedding 模型

### 3.2 向量相似度

两个向量越相似，对应的文本语义越接近。

**余弦相似度**（最常用）：
```
相似度 = cos(A, B) = (A·B) / (|A| × |B|)

范围：-1 到 1
  1  = 完全相同
  0  = 完全无关
  -1 = 完全相反
```

你不需要自己算，向量数据库会自动算。

### 3.3 向量数据库

专门存储和检索向量的数据库。核心操作：存入向量 + 按相似度查找最近的 K 个。

| 数据库 | 特点 | 适合 |
|--------|------|------|
| **Chroma** | 轻量、Python原生、嵌入式 | **学习/小项目（你用这个）** |
| Pinecone | 云服务、托管型 | 生产环境 |
| Milvus | 分布式、高性能 | 大规模数据 |
| FAISS | Facebook出品、纯向量检索 | 研究/嵌入到其他系统 |

面试被问"为什么选 Chroma"：
> Chroma 是 Python 原生的嵌入式向量数据库，不需要单独部署服务，适合中小规模项目。支持持久化存储，API 简洁，和 LangChain 集成好。

### 3.4 文本分割（Chunking）

**为什么要分割？**
- 一个 PDF 可能有几万字，直接存入向量库效果差
- LLM 上下文有长度限制，不能把整个文档塞进去
- 检索时需要定位到具体段落，而不是整个文档

**分割策略**：

| 策略 | 方法 | 优缺点 |
|------|------|--------|
| 固定大小 | 每 500 字切一段 | 简单但可能切断句子 |
| 按段落 | 按 `\n\n` 分段 | 保持段落完整 |
| 递归分割 | 先按标题→再按段落→再按句子 | **推荐，LangChain 默认** |
| 语义分割 | 按语义变化点切 | 效果最好但计算量大 |

**关键参数**：
- `chunk_size`：每段多长（通常 500-1000 字符）
- `chunk_overlap`：相邻段重叠多少（通常 50-200 字符，防止切断上下文）

## 四、RAG 效果优化方向

### 4.1 检索质量优化

| 方法 | 原理 | 效果 |
|------|------|------|
| 混合检索 | 向量检索 + 关键词检索（BM25）结合 | 兼顾语义和精确匹配 |
| 重排序 | 检索后用另一个模型对结果重新排序 | 显著提升准确率 |
| 查询改写 | 把用户问题改写成更好的检索 query | 提高召回率 |

### 4.2 生成质量优化

| 方法 | 原理 |
|------|------|
| 好的 Prompt | Day 9 学的 RAG Prompt 模板 |
| 引用来源 | 让模型标注答案来自哪个文档 |
| 对话增强 | 多轮对话时把历史也考虑进去 |

这些会在 Day 15 和项目开发阶段详细学。

## 五、RAG vs 微调（Fine-tuning）

面试可能会问"为什么用 RAG 而不是微调"：

| | RAG | 微调 |
|--|-----|------|
| 知识更新 | 更新文档即可，秒级 | 重新训练，小时/天级 |
| 成本 | 低（只需向量库） | 高（GPU训练） |
| 可解释性 | 能标注来源 | 黑盒 |
| 适合场景 | 知识密集型问答 | 改变模型行为/风格 |
| 你的项目 | **用 RAG** | 不需要 |

## 六、面试必背

1. **RAG 是什么？** → 检索增强生成，先从知识库检索相关文档，再把文档作为上下文让 LLM 生成回答
2. **RAG 解决什么问题？** → 知识过时和幻觉（编造内容）
3. **RAG 的完整流程？** → 离线：文档→解析→分割→Embedding→存入向量库。在线：问题→Embedding→检索→拼Prompt→LLM回答
4. **Embedding 是什么？** → 把文本转成固定维度的向量，语义相近的文本向量距离近
5. **为什么要文本分割？** → 整文档太长影响检索精度和 LLM 上下文限制
6. **chunk_size 怎么选？** → 通常 500-1000 字符，overlap 50-200，具体看文档类型和检索效果
7. **为什么选 Chroma？** → Python 原生、嵌入式、不需额外部署、API 简洁、适合中小项目
