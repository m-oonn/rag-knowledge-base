## 二、混合检索：BM25 + 向量检索

### 2.1 为什么要混合？

| 检索方式 | 擅长 | 不擅长 | 例子 |
|----------|------|--------|------|
| **向量检索** | 语义相似 | 精确关键词 | "怎么做Web开发" 能找到 "FastAPI教程" |
| **BM25关键词** | 精确匹配 | 语义理解 | "FastAPI" 能精确匹配包含这个词的文档 |
| **混合** | 兼顾两者 | - | 同时利用语义和关键词优势 |

**真实案例**：

```
查询: "chromadb persist_directory 参数"

向量检索结果（按语义）:
  1. "Chroma 是一个嵌入式向量数据库..."  (语义相关但没提到参数)
  2. "向量数据库的持久化存储..."          (概念相关)

BM25 结果（按关键词）:
  1. "persist_directory='./chroma_db'"    (精确匹配参数名!)
  2. "chromadb.PersistentClient(path=...)" (匹配产品名)

混合结果: 两者合并，效果最好
```

### 2.2 BM25 算法简解

BM25 是经典的关键词检索算法，搜索引擎（如 Elasticsearch）的核心。

**核心思想**：一个词在某文档中出现越多（TF），同时在所有文档中出现越少（IDF），这个词对该文档的重要性越高。

```
BM25(q, d) = SUM[ IDF(qi) * TF(qi, d) ]

其中:
  IDF(qi) = log((N - n(qi) + 0.5) / (n(qi) + 0.5))
    N = 文档总数
    n(qi) = 包含词 qi 的文档数
    越稀有的词，IDF 越高

  TF(qi, d) = (f(qi, d) * (k1 + 1)) / (f(qi, d) + k1 * (1 - b + b * |d|/avgdl))
    f(qi, d) = 词 qi 在文档 d 中出现的次数
    |d| = 文档 d 的长度
    avgdl = 所有文档的平均长度
    k1 = 1.5 (调参，控制词频饱和度)
    b = 0.75 (调参，控制文档长度的影响)
```

**简单理解**：

```
"Python" 出现在 90% 的文档中 → IDF 低 → 不重要
"chromadb" 只出现在 2% 的文档中 → IDF 高 → 很重要

文档A 提到 "chromadb" 5 次 → TF 高 → 和查询更相关
文档B 提到 "chromadb" 1 次 → TF 低 → 相关性较低
```

### 2.3 混合检索的融合策略

**倒数排名融合（Reciprocal Rank Fusion, RRF）**：

```
RRF_score(d) = SUM[ 1 / (k + rank_i(d)) ]

  k = 60 (常数，防止排名第1的权重过大)
  rank_i(d) = 文档 d 在第 i 个检索器中的排名

示例:
  文档A: 向量检索排名第1, BM25排名第3
  RRF(A) = 1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.0323

  文档B: 向量检索排名第5, BM25排名第1
  RRF(B) = 1/(60+5) + 1/(60+1) = 0.0154 + 0.0164 = 0.0318

  文档A 综合排名更高（两个检索器都觉得它相关）
```

## 三、重排序（Reranking）

### 3.1 为什么需要重排序？

```
检索阶段（粗排）:
  从 10000 个文档中快速找到 Top-20 → 用 Embedding（Bi-encoder）
  速度快，但精度一般

重排序阶段（精排）:
  对 Top-20 重新打分排序 → 用 Cross-encoder
  速度慢，但精度高

两阶段架构:
  全量文档 --[粗排]--> Top-20 --[精排]--> Top-5 --> 送给 LLM
  10000个              20个              5个

类比: 海选（粗排）→ 决赛（精排）
```

### 3.2 Bi-encoder vs Cross-encoder

```
Bi-encoder（用于粗排/检索）:
  Query: "什么是RAG" → Encoder → [0.1, 0.3, ...]
  Doc:   "RAG是检索..." → Encoder → [0.2, 0.4, ...]
  然后计算向量相似度
  特点: Query 和 Doc 独立编码，可以预计算 Doc 向量

Cross-encoder（用于精排/重排序）:
  [Query, Doc] → 一起输入 → Encoder → 相关性分数 0.92
  特点: Query 和 Doc 一起编码，交互更充分，精度更高
  缺点: 不能预计算，每次都要跑模型，速度慢
```

| | Bi-encoder | Cross-encoder |
|---|---|---|
| 输入方式 | Query 和 Doc 分别编码 | Query + Doc 一起编码 |
| 速度 | 快（可预计算Doc向量） | 慢（每对都要计算） |
| 精度 | 一般 | 高 |
| 用途 | 粗排/检索 | 精排/重排序 |
| 代表 | sentence-transformers | cross-encoder 模型 |

### 3.3 常用重排序模型

| 模型 | 来源 | 特点 |
|------|------|------|
| **bge-reranker-base** | BAAI(智源) | 中文效果好，适合国内项目 |
| cohere-rerank | Cohere | API 服务，方便但收费 |
| ms-marco-MiniLM | Microsoft | 英文效果好，轻量 |

```python
# 使用示例（需要安装 sentence-transformers）
from sentence_transformers import CrossEncoder

model = CrossEncoder("BAAI/bge-reranker-base")
pairs = [
    ["什么是RAG", "RAG是检索增强生成技术"],
    ["什么是RAG", "今天天气真好"],
]
scores = model.predict(pairs)
# scores: [0.95, 0.02]  → 第一对高度相关
```

## 四、查询改写（Query Transformation）

### 4.1 为什么要改写？

用户的原始问题往往不适合直接检索：

| 原始查询 | 问题 | 改写后 |
|----------|------|--------|
| "fastapi 咋装" | 口语化 | "FastAPI 安装方法" |
| "RAG" | 太短，歧义 | "RAG 检索增强生成 原理 流程" |
| "为什么我的API返回422" | 包含无关词 | "FastAPI 422 错误 数据验证 Pydantic" |
| "之前说的那个数据库" | 指代不清（多轮对话） | "Chroma 向量数据库 配置方法" |

### 4.2 改写策略

**策略 1：关键词扩展**

```
原始: "fastapi 安装"
扩展: "fastapi 安装 pip uvicorn 快速开始 setup"
方法: 添加同义词和相关词
```

**策略 2：LLM 改写**

```python
prompt = """请将以下用户问题改写为更适合知识库检索的查询。
要求：去掉口语化表达，补充关键术语，保持语义不变。

用户问题: {question}
改写后的检索查询:"""
```

**策略 3：HyDE（Hypothetical Document Embedding）**

```
思路: 不直接用问题检索，而是先让 LLM 生成一个"假答案"，用假答案去检索

步骤:
  1. 用户问: "什么是RAG"
  2. LLM 生成假答案: "RAG是检索增强生成，它先从知识库检索相关文档..."
  3. 用假答案的 Embedding 去检索（假答案和真文档更相似）

效果: 比直接用问题检索好，因为"答案"和"文档"在向量空间更近
```

## 五、评估指标

### 5.1 检索质量指标

| 指标 | 公式 | 含义 |
|------|------|------|
| **Recall@K** | 检索到的相关文档数 / 所有相关文档数 | 召回率：找全了多少 |
| **Precision@K** | 检索到的相关文档数 / K | 精确率：找到的有多少是对的 |
| **MRR** | 1/第一个相关文档的排名 | 第一个正确答案排多前 |

**示例**：

```
数据库中有 3 篇关于 "FastAPI安装" 的文档
检索 Top-5，命中了其中 2 篇（排在第1和第4位）

Recall@5 = 2/3 = 0.667     (找到了2/3的相关文档)
Precision@5 = 2/5 = 0.4    (5个结果中2个相关)
MRR = 1/1 = 1.0            (第一个结果就是相关的)
```

### 5.2 实际评估流程

```
Step 1: 准备测试集
  - 20-50 个测试问题
  - 每个问题标注正确答案来自哪些文档（ground truth）

Step 2: 跑检索
  - 对每个问题执行检索，记录 Top-K 结果

Step 3: 计算指标
  - 对比检索结果和 ground truth
  - 计算平均 Recall@K, Precision@K, MRR

Step 4: 调优
  - 调整 chunk_size, top_k, 检索策略
  - 重新评估，看指标是否提升
```

## 七、面试常问

### Q1: 基础 RAG 有什么问题？你怎么优化？

> 基础 RAG 的问题：1）纯向量检索对精确关键词匹配不够好；2）粗排结果精度不够；3）用户查询表达不规范。
> 优化三板斧：混合检索（BM25+向量+RRF融合）提升召回率；重排序（Cross-encoder精排）提升精确率；查询改写（关键词扩展/LLM改写）优化检索输入。

### Q2: BM25 和向量检索有什么区别？

> BM25 基于关键词匹配（词频*逆文档频率），擅长精确匹配但不理解语义。向量检索基于 Embedding 语义相似度，擅长语义匹配但可能漏掉精确关键词。混合使用效果最好。

### Q3: 什么是 Reranking？为什么有效？

> Reranking 是在粗排（Bi-encoder检索）之后，用 Cross-encoder 对 Top-K 结果重新打分排序。Cross-encoder 把 Query 和 Doc 一起编码，交互更充分，精度更高。但速度慢，所以只对少量候选做精排。

### Q4: RRF 是什么？怎么用？

> Reciprocal Rank Fusion，倒数排名融合。用于合并多个检索器的结果。公式：RRF(d) = SUM[1/(k+rank_i(d))]，k通常取60。在两个检索器中排名都靠前的文档，RRF分数最高。

### Q5: 你怎么评估 RAG 效果？

> 准备测试集（问题+标注答案来源），计算 Recall@K（召回率）、Precision@K（精确率）、MRR（平均倒数排名）。每次优化后重新评估，确保指标有提升。
