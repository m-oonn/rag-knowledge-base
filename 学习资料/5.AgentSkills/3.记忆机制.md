# Day 33：记忆机制（Memory）

> LLM 天生"健忘"——每次调用都是独立的，不记得之前说过什么。
> 今天学习怎么给 Agent 加上记忆，让它像真人一样记住对话上下文。

---

## 一、为什么 Agent 需要记忆？

### 1.1 LLM 的致命缺陷：无状态

```
第1轮: 用户: "我叫小明，是大三学生"
       LLM: "你好小明！有什么可以帮你的？"

第2轮: 用户: "我学什么专业来着？"
       LLM: "抱歉，我不知道你学什么专业。"  ← 完全不记得上一轮！
```

**原因**：LLM 的每次 API 调用都是**无状态**的。模型不会保存任何对话历史。上一轮的对话对下一轮来说完全不存在。

### 1.2 解决方案：手动管理记忆

```
核心思路: 把历史对话塞进 Prompt，让 LLM "以为"自己记得

第1轮:
  messages = [
    {"role": "user", "content": "我叫小明，是大三学生"}
  ]
  → LLM 回复: "你好小明！"

第2轮:
  messages = [
    {"role": "user", "content": "我叫小明，是大三学生"},     ← 历史
    {"role": "assistant", "content": "你好小明！"},          ← 历史
    {"role": "user", "content": "我学什么专业来着？"}        ← 新消息
  ]
  → LLM 看到上下文: "你叫小明，大三学生"
  → LLM 回复: "你之前只说了是大三学生，没告诉我专业哦~"  ← 能回忆了！
```

### 1.3 记忆的本质

```
记忆 = 在每次调用时，把相关的历史信息拼进 messages

不是 LLM 真的"记住"了，而是你每次都把上下文"提醒"给它。
就像考试时把小抄塞在卷子里。
```

## 二、记忆类型全景

### 2.1 按时间维度分

```
┌─────────────────────────────────────────────────────┐
│                    Agent 记忆体系                      │
├───────────────────┬─────────────────────────────────┤
│   短期记忆         │   长期记忆                        │
│   (对话内)         │   (跨对话)                        │
├───────────────────┼─────────────────────────────────┤
│ Buffer Memory     │ Vector DB 存储                    │
│ Window Memory     │ 实体记忆 (Entity Memory)          │
│ Summary Memory    │ 用户画像/偏好                     │
│ Token Buffer      │ 知识图谱                          │
├───────────────────┼─────────────────────────────────┤
│ 存在: messages 列表│ 存在: 外部数据库                   │
│ 生命周期: 单次对话  │ 生命周期: 永久                    │
└───────────────────┴─────────────────────────────────┘
```

### 2.2 五种常用记忆策略

| 记忆类型 | 原理 | 优点 | 缺点 | 适合场景 |
|---------|------|------|------|---------|
| Buffer | 存所有对话 | 信息完整 | token 爆炸 | 短对话(<10轮) |
| Window | 只存最近 N 轮 | 控制 token | 丢失早期信息 | 客服/问答 |
| Summary | 摘要旧对话 | 省 token 又保留要点 | 需要额外 LLM 调用 | 长对话 |
| Token Buffer | 按 token 数截断 | 精确控制上下文 | 可能切断对话 | token 敏感场景 |
| Vector | 存入向量库按需检索 | 海量记忆 | 检索延迟 | 跨对话记忆 |

## 三、Buffer Memory（缓冲记忆）

### 3.1 原理

最简单的记忆方式：保存所有对话历史，每次都全部发给 LLM。

```
messages = [
    {"role": "user", "content": "我叫小明"},
    {"role": "assistant", "content": "你好小明"},
    {"role": "user", "content": "我在学 Python"},
    {"role": "assistant", "content": "Python 很好！"},
    {"role": "user", "content": "推荐一本书"},          ← 新消息
    ... 全部发给 LLM
]
```

### 3.2 问题

```
对话轮数:    token 消耗:
  5轮        ~500 tokens     ← 没问题
  20轮       ~2000 tokens    ← 开始贵了
  100轮      ~10000 tokens   ← 可能超出上下文限制！
```

### 3.3 LangChain 实现

```python
from langchain.memory import ConversationBufferMemory

memory = ConversationBufferMemory(return_messages=True)

# 添加对话
memory.save_context(
    {"input": "我叫小明"},
    {"output": "你好小明！"}
)

# 获取历史
history = memory.load_memory_variables({})
# {"history": [HumanMessage("我叫小明"), AIMessage("你好小明！")]}
```

## 四、Window Memory（窗口记忆）

### 4.1 原理

只保留最近 N 轮对话，更早的自动丢弃。

```
k=3 (保留最近3轮):

Round 1: "我叫小明" → "你好小明"          [保留]
Round 2: "我学 Python" → "很好"           [保留]
Round 3: "推荐一本书" → "推荐《流畅的Python》" [保留]
Round 4: "还有吗？" → ...

此时发给 LLM 的 messages 只有 Round 2, 3, 4
Round 1 被丢弃了！→ LLM 不再知道用户叫小明
```

### 4.2 k 值选择

| k 值 | 效果 | 适合 |
|------|------|------|
| k=1 | 几乎无记忆，只知道上一轮 | 简单问答 |
| k=3 | 短期上下文，平衡 token | 客服对话 |
| k=5 | 较好的上下文连续性 | 技术讨论 |
| k=10 | 丰富上下文但 token 多 | 复杂推理 |

### 4.3 LangChain 实现

```python
from langchain.memory import ConversationBufferWindowMemory

memory = ConversationBufferWindowMemory(k=3, return_messages=True)

# k=3 意味着只保留最近3轮人机对话
```

## 五、Summary Memory（摘要记忆）

### 5.1 原理

用 LLM 把旧的对话历史压缩成一段摘要，新对话 + 摘要一起发给 LLM。

```
原始对话（10轮，2000 tokens）:
  Round 1: 用户自我介绍（叫小明，大三，AI专业）
  Round 2: 讨论了 Python 基础
  Round 3-8: 学习了 FastAPI、异步编程等
  Round 9: 讨论了 RAG 原理
  Round 10: 新问题

  ↓ LLM 摘要 ↓

摘要（200 tokens）:
  "用户小明，大三 AI 专业学生。已学习 Python 基础、FastAPI、
   异步编程、RAG 原理。目前在准备暑期实习项目。"

发给 LLM 的 messages:
  [摘要] + [最近2轮原始对话] + [新问题]
  = ~400 tokens（节省了 80%）
```

### 5.2 流程图

```
                 对话历史（越来越长）
                       │
          ┌────────────┼────────────┐
          │ 旧对话      │ 最近对话    │
          │ (Round 1-8) │ (Round 9-10)│
          └──────┬─────┘└────────────┘
                 │                │
            LLM 摘要              │
                 │                │
            "用户小明..."         原始消息
                 │                │
                 └──────┬─────────┘
                        │
                  拼接后发给 LLM
                        │
                     生成回答
```

### 5.3 代价

- 需要额外的 LLM 调用来生成摘要（增加延迟和成本）
- 摘要可能丢失细节（"你第3轮说的那个例子"就找不回来了）

### 5.4 LangChain 实现

```python
from langchain.memory import ConversationSummaryMemory

memory = ConversationSummaryMemory(
    llm=llm,                    # 用来生成摘要的 LLM
    return_messages=True
)
```

## 六、Entity Memory（实体记忆）

### 6.1 原理

跟踪对话中提到的关键实体（人名、项目名、技术名词等），为每个实体维护一段描述。

```
对话:
  用户: "我叫小明，在用 FastAPI 做一个 RAG 项目"
  
实体记忆:
  小明: 用户本人，正在做 RAG 项目
  FastAPI: 用户正在使用的 Web 框架
  RAG项目: 用户正在开发的项目

后续对话:
  用户: "小明的项目进展如何？"
  → 系统检索实体 "小明" 的信息 → 拼入 Prompt
```

### 6.2 适用场景

- 客户关系管理（记住客户信息）
- 项目助手（记住项目背景和技术栈）
- 教育助手（记住学生的学习进度）

## 七、Vector Memory（向量记忆）

### 7.1 原理

把对话历史存入向量数据库，需要时按相似度检索最相关的历史。

```
存储:
  每轮对话 → Embedding → 存入 Chroma/FAISS

检索:
  新问题 → Embedding → 在向量库中找最相似的历史对话 → 拼入 Prompt

优势: 可以跨对话记忆（"上周你问过关于 FastAPI 的问题..."）
```

### 7.2 与 RAG 的关系

```
RAG（Day 10 学的）:
  文档 → 向量库 → 检索 → 拼入 Prompt → 回答问题

Vector Memory:
  对话历史 → 向量库 → 检索 → 拼入 Prompt → 记住上下文

本质一样！只是"文档"换成了"对话历史"
```

### 7.3 实现方式

```python
# 概念代码（Day 33 Demo 中有完整实现）
import chromadb

# 创建记忆向量库
collection = chroma_client.get_or_create_collection("chat_memory")

# 存储对话
collection.add(
    documents=["用户说他叫小明，大三AI专业"],
    ids=["conv_001"]
)

# 检索相关记忆
results = collection.query(
    query_texts=["用户叫什么名字？"],
    n_results=3
)
```

## 八、如何选择记忆策略？

### 8.1 决策树

```
你的对话通常有多长？
│
├── < 10 轮 → Buffer Memory（最简单，够用）
│
├── 10-50 轮 → Window Memory（k=5-10）
│               └── 需要记住早期关键信息？ → Summary Memory
│
├── 50+ 轮 → Summary Memory（压缩旧对话）
│
└── 跨对话记忆？ → Vector Memory（永久存储）
    └── 需要跟踪具体实体？ → Entity Memory
```

### 8.2 组合使用

实际项目中通常组合多种记忆：

```
推荐组合: Window + Vector

Window Memory: 保留最近 5 轮完整对话（短期上下文）
Vector Memory: 存储所有历史的关键信息（长期检索）

每次调用:
  messages = [系统提示] + [向量检索到的相关历史] + [最近5轮] + [新消息]
```

## 九、Token 预算管理

### 9.1 问题

LLM 的上下文窗口有限：

| 模型 | 上下文限制 |
|------|-----------|
| GPT-3.5 | 4K / 16K tokens |
| GPT-4 | 8K / 128K tokens |
| Qwen2.5:7b | 32K tokens |
| DeepSeek | 64K / 128K tokens |

你需要在有限的 token 预算内分配给：系统提示 + 记忆 + 工具结果 + 用户消息

### 9.2 Token 预算分配

```
以 4K token 为例:

┌─────────────────────────────────────┐
│  System Prompt     |  500 tokens    │  ← 角色定义、规则
│  Memory/History    | 1500 tokens    │  ← 对话历史/记忆
│  Tool Results      |  500 tokens    │  ← 工具返回的数据
│  User Message      |  500 tokens    │  ← 当前用户输入
│  Reserved (output) | 1000 tokens    │  ← 留给模型生成回答
│─────────────────────────────────────│
│  Total             | 4000 tokens    │
└─────────────────────────────────────┘
```

### 9.3 超预算怎么办？

| 策略 | 做法 |
|------|------|
| 截断 | 丢弃最早的对话 |
| 摘要 | 压缩旧对话为摘要 |
| 选择性检索 | 只检索相关的历史 |
| 增大窗口 | 用更大上下文的模型 |

## 十、面试常问

1. **为什么 LLM 需要 Memory？** → LLM 每次调用无状态，不会自动记住之前的对话。Memory 通过把历史信息拼入 Prompt 来模拟记忆
2. **Buffer vs Window vs Summary Memory 区别？** → Buffer 存所有对话（简单但耗 token），Window 只存最近 N 轮（省 token 但丢信息），Summary 把旧对话压缩为摘要（平衡但需额外 LLM 调用）
3. **怎么实现跨对话记忆？** → 用向量数据库存储历史对话，每次对话时检索相关历史拼入 Prompt
4. **Memory 和 RAG 有什么关系？** → 本质相同，都是"检索相关信息 → 拼入 Prompt"，RAG 检索文档，Memory 检索对话历史
5. **Token 预算不够怎么办？** → 截断旧对话 / 摘要压缩 / 向量检索只取相关部分 / 用更大上下文模型
6. **你项目中怎么使用 Memory？** → 短期用 Window Memory 保持对话连贯，长期用向量数据库存储用户偏好和关键信息
7. **Entity Memory 适合什么场景？** → 需要跟踪和更新特定实体信息的场景，如客户管理系统、项目助手
