## 一、Agent 循环 —— LangGraph 最核心的模式

### 1.1 什么是 Agent 循环？

Agent 不是"调一次 LLM 就完事"，而是一个**循环**：

```
                 ┌──────────────────────────┐
                 │                          │
                 v                          │
START ──→ LLM_Node ──→ should_continue? ───┤
                 │          │               │
                 │     有 tool_call         │
                 │          │               │
                 │          v               │
                 │     Tool_Node ───────────┘
                 │
            没有 tool_call
                 │
                 v
                END
```

**执行过程**：
1. LLM 看到用户问题 + 可用工具列表
2. LLM 决定：需要调工具？还是直接回答？
3. 如果需要调工具 --> Tool_Node 执行工具 --> 结果返回给 LLM --> 回到步骤 2
4. 如果不需要工具 --> 直接输出答案 --> END

### 1.2 这就是 ReAct 模式

```
Thought:  用户想知道北京天气，我需要调 weather 工具
Action:   weather_tool(city="北京")
Observation: 北京今天晴，25度
Thought:  我已经得到了天气信息，可以回答了
Answer:   北京今天是晴天，气温 25 度。
```

LangGraph 用**条件边 + 循环**实现了这个模式，不需要手动写 while 循环。

## 二、条件边深入

### 2.1 路由函数的多种写法

```python
# 写法 1：返回字符串 key
def route_fn(state):
    if condition_a(state):
        return "go_a"
    return "go_b"

graph.add_conditional_edges("source", route_fn, {
    "go_a": "node_a",
    "go_b": "node_b",
})

# 写法 2：直接返回节点名（不需要映射表）
def route_fn(state):
    if condition_a(state):
        return "node_a"
    return "node_b"

graph.add_conditional_edges("source", route_fn, ["node_a", "node_b"])
```

### 2.2 Agent 中的条件边

```python
from langgraph.prebuilt import tools_condition

# tools_condition 是 LangGraph 内置的路由函数：
# - 如果最后一条消息包含 tool_calls --> 返回 "tools"
# - 否则 --> 返回 END
graph.add_conditional_edges("llm_node", tools_condition)
```

这是最常用的模式，不需要自己写路由逻辑。

## 三、Tool Calling Agent 实现

### 3.1 完整结构

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

# 1. 定义状态
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

# 2. 定义工具
@tool
def search(query: str) -> str:
    """搜索工具"""
    return f"搜索结果: {query}"

tools = [search]

# 3. LLM 节点（绑定工具）
def llm_node(state):
    response = llm.bind_tools(tools).invoke(state["messages"])
    return {"messages": [response]}

# 4. 工具执行节点
tool_node = ToolNode(tools)

# 5. 构建图
graph = StateGraph(AgentState)
graph.add_node("llm", llm_node)
graph.add_node("tools", tool_node)

graph.add_edge(START, "llm")
graph.add_conditional_edges("llm", tools_condition)
graph.add_edge("tools", "llm")  # 工具执行完回到 LLM

app = graph.compile()
```

### 3.2 执行流程

```
invoke({"messages": [("user", "北京天气怎么样？")]})

  --> LLM: "我需要调 weather 工具"  (产生 tool_call)
  --> tools_condition: 有 tool_call --> 去 tools 节点
  --> tools: 执行 weather("北京") --> "晴天 25度"
  --> 回到 LLM: "根据工具结果，北京今天晴天 25 度"
  --> tools_condition: 没有 tool_call --> END
```

## 四、Human-in-the-loop

### 4.1 为什么需要人工介入？

- Agent 要执行危险操作（删文件、发邮件）时，需要人类确认
- Agent 不确定时，让人类做选择
- 审批流程：Agent 拟定方案，人类批准后执行

### 4.2 实现方式

```python
from langgraph.checkpoint.memory import MemorySaver

# 方式 1：使用 interrupt_before 在某个节点前暂停
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["dangerous_node"]
)

# 执行到 dangerous_node 前会暂停
result = app.invoke(input_data, config={"configurable": {"thread_id": "1"}})
# result 中包含暂停信息

# 用户确认后继续执行
result = app.invoke(None, config={"configurable": {"thread_id": "1"}})
```

```python
# 方式 2：在节点内部通过 interrupt() 主动暂停
from langgraph.types import interrupt, Command

def review_node(state):
    """审核节点：暂停等待人工确认"""
    plan = state["plan"]
    # 暂停图，把 plan 展示给用户
    user_decision = interrupt({"plan": plan, "question": "是否执行？"})
    if user_decision == "yes":
        return {"approved": True}
    else:
        return {"approved": False}
```

### 4.3 Checkpointer

Human-in-the-loop 需要**持久化状态**（暂停后能恢复）：

| Checkpointer | 特点 | 适合 |
|---------------|------|------|
| MemorySaver | 内存中存储，重启就丢 | **开发调试** |
| SqliteSaver | SQLite 文件存储 | 单机生产 |
| PostgresSaver | PostgreSQL 存储 | 多节点生产 |

## 五、子图（Subgraph）

### 5.1 为什么需要子图？

当图变得复杂时，可以把一部分逻辑**封装成子图**，然后嵌入到主图中。

```
主图:
  START → preprocessing → agent_subgraph → postprocessing → END

agent_subgraph (子图):
  START → llm → tools_condition → tools → llm → ... → END
```

### 5.2 实现方式

```python
# 子图：独立编译
sub_graph = StateGraph(SubState)
sub_graph.add_node(...)
sub_app = sub_graph.compile()

# 主图：把子图当作普通节点添加
main_graph = StateGraph(MainState)
main_graph.add_node("agent", sub_app)  # 子图作为节点
main_graph.add_edge(START, "agent")
main_graph.add_edge("agent", END)
```

**注意**：子图的 State 和主图的 State 需要有共同的字段（至少 messages），LangGraph 会自动在主/子状态之间映射。

## 六、错误处理

### 6.1 节点级错误处理

```python
def safe_tool_node(state):
    """带错误处理的工具节点"""
    try:
        result = execute_tool(state)
        return {"result": result, "error": None}
    except Exception as e:
        return {"result": None, "error": str(e)}

def route_after_tool(state):
    if state.get("error"):
        return "error_handler"
    return "next_node"
```

### 6.2 重试模式

```
         ┌──────────────┐
         │              │
         v              │
  tool_node ──→ check ──┤  (retry_count < 3 且有错误 --> 重试)
                  │
             成功或超过重试次数
                  │
                  v
             next_node
```

```python
class RetryState(TypedDict):
    messages: Annotated[list, add_messages]
    error: str
    retry_count: int

def check_result(state):
    if state.get("error") and state["retry_count"] < 3:
        return "retry"
    return "continue"

graph.add_conditional_edges("tool", check_result, {
    "retry": "tool",       # 回到 tool 重试
    "continue": "next",
})
```

### 6.3 Fallback 模式

```
                    ┌── primary_llm ──→ success? ──→ next
  START → router ──┤
                    └── fallback_llm ──→ next
```

当主 LLM 失败时自动切换到备用 LLM。

## 八、对比：LangGraph Agent vs LangChain AgentExecutor

| 特性 | AgentExecutor (旧) | LangGraph Agent (新) |
|------|-------------------|---------------------|
| 状态管理 | 隐式内部状态 | 显式 TypedDict |
| 循环控制 | 固定的内部循环 | 自定义条件边 |
| 错误处理 | 有限（max_iterations） | 完全自定义 |
| 人工介入 | 不支持 | 原生 interrupt |
| 流式输出 | 基础支持 | 完整事件流 |
| 自定义程度 | 低 | 高 |
| 调试难度 | 黑盒 | 每个节点可观察 |
| 官方推荐 | 已逐步废弃 | **推荐使用** |

**结论**：新项目一律用 LangGraph，AgentExecutor 只在老代码中见到。

## 九、面试常问

1. **LangGraph 怎么实现 Agent 循环？** --> 用条件边判断 LLM 输出是否包含 tool_call：有则跳到 Tool 节点执行，完毕后回到 LLM 节点；无则跳到 END。循环通过条件边自然形成
2. **tools_condition 做了什么？** --> 检查最后一条 AI 消息是否包含 tool_calls：有则路由到 "tools"，无则路由到 END
3. **Human-in-the-loop 怎么实现？** --> 使用 Checkpointer 持久化状态 + interrupt_before/interrupt() 在指定节点暂停，用户确认后恢复执行
4. **Agent 中工具执行失败怎么处理？** --> 节点内 try/except 捕获异常，将错误信息写入 state，用条件边路由到 error_handler 或重试节点
5. **ToolNode 是什么？** --> LangGraph 内置的工具执行节点，自动解析 AI 消息中的 tool_calls，执行对应工具函数，将结果作为 ToolMessage 返回
6. **什么场景需要子图？** --> 当图逻辑复杂时，把一部分功能封装成子图，提高可读性和可复用性。例如把 Agent 循环封装成子图嵌入到更大的工作流中
7. **LangGraph 和 AgentExecutor 怎么选？** --> 新项目用 LangGraph（更灵活、可控、官方推荐），AgentExecutor 已逐步废弃
